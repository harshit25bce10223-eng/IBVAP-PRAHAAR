## Root causes

**A — WDDM pin-memory crash (attempt 1).** Ultralytics hardcodes `pin_memory=True` when workers>0 (`data/build.py:324/366`); on this display-attached WDDM GPU the pin thread died with “resource already mapped”. Fix already deployed: `--no-pin-memory` (patches `Tensor.pin_memory` to pass-through; recorded in run manifest).

**B — System commit exhaustion (attempt 2, the deeper cause).** workers=4 → ultralytics eagerly builds **12** dataloader processes (train+test pools spawn at loader construction, `InfiniteDataLoader`), ≈ 530 MB private commit each ≈ 6.4 GB. With the wrapper+CUDA+dataset caches the system commit hit **31.37 / 31.58 GB (≈ 210 MB headroom)** and a 1.17 MiB numpy allocation failed inside a worker; numpy 2.4.6/cv2 5.0.0 surfaced it as `SystemError` (misleading, not a cv2 bug per se). Fix: RAM-aware cap in both scripts — machines < 12 GiB total RAM run **workers=2** (`workers_requested` / `workers_note` recorded in the run manifest; resume passes the capped value explicitly, allowed by ultralytics `check_resume`).

**C — Chain race + destructive OOM heuristic (the data loss).** `launch_train` is blocking; when the chain's child exited, its crash path **did not check whether another trainer was already running** (a manual relaunch), relaunched a duplicate → VRAM duel → simulated “OOM”. The OOM branch then did `rm -rf` + batch-halving **even for the external exp001 run**, wiping the epoch 1–3 lineage. Fix: `run_sweep_302.sh` v2 —
1. **race guard**: every crash path re-checks `training_alive()`; if any `train_detector` process is live it WAITS instead of relaunching;
2. **OOM fresh-wipe gated to non-external runs** (`[ "$external" != "1" ]`); external exp001 is resume-only — never batch-halved, never `rm -rf`'ed.

**Process rule:** never manually intervene in a chain-managed run while the chain bash is alive — stop the chain first (v2 makes coexistence safe, but one writer per run dir remains the rule).
